# Deployment Checklist — HawkerCredit Quantum

Work through this top to bottom. Each section assumes the previous one is
done. See `FINAL_README.md` for the "why" behind each step.

## Render (backend + database)
- [ ] Push this repo to GitHub/GitLab (Render Blueprints deploy from a repo).
- [ ] Render dashboard → New → Blueprint → select this repo.
- [ ] Confirm Render reads `render.yaml` and shows **two** resources to
      create: the `hawkercredit-db` Postgres database and the
      `hawkercredit-backend` web service.
- [ ] Click Apply / Deploy.
- [ ] Once deployed, open the service's Environment tab and **copy the
      auto-generated `STAFF_BOOTSTRAP_SECRET` value somewhere safe** — you
      need it once, before you have an admin account.
- [ ] Confirm the build log shows Docker installing `tesseract-ocr` and
      `pip install -r requirements.txt` completing without errors.
- [ ] Hit `https://<your-service>.onrender.com/health` → expect HTTP 200
      JSON with `"status": "healthy"`.
- [ ] Hit `https://<your-service>.onrender.com/` → expect HTTP 200 JSON
      service banner (not a 404).

## Environment variables (Render service → Environment tab)
- [ ] `ENVIRONMENT=production` (set by the blueprint already — confirm)
- [ ] `JWT_SECRET` — auto-generated by the blueprint — confirm it's set,
      don't overwrite it.
- [ ] `STAFF_BOOTSTRAP_SECRET` — auto-generated — confirm it's set.
- [ ] `DATABASE_URL` — auto-wired to the managed Postgres instance via
      `fromDatabase` — confirm it's populated, not blank.
- [ ] `DEMO_SEED_ON_STARTUP=true` (or `false` if you want a clean,
      non-demo deployment from day one).
- [ ] `CORS_ORIGINS` — leave as `http://localhost:3000` for now; **you'll
      come back and update this after the Vercel step below.**

## Database migration & seed
- [ ] Confirm the backend logs on first boot show tables being created
      against the fresh Postgres database (SQLAlchemy `create_all`/Alembic,
      depending on what's configured) with no connection errors.
- [ ] If `DEMO_SEED_ON_STARTUP=true`, confirm the logs show seeding running
      once and completing (roughly 100 vendors, 10 lenders, 1 admin).
- [ ] Trigger a redeploy (or restart) and confirm the seed step does **not**
      duplicate rows or error out on the second run (it's designed to be
      idempotent — this is worth actually checking once).

## Vercel (frontend)
- [ ] Import this repo into Vercel as a new project.
- [ ] Confirm Vercel picks up root `vercel.json` (Next.js framework,
      `cd frontend && npm ci && npm run build`) — check the build settings
      panel shows this instead of Vercel's generic auto-detected defaults.
- [ ] Project Settings → Environment Variables → add for **both**
      Production and Preview:
  - [ ] `NEXT_PUBLIC_API_URL` = `https://<your-render-service>.onrender.com/api/v1`
  - [ ] `BACKEND_URL` = `https://<your-render-service>.onrender.com`
- [ ] Deploy.
- [ ] Visit the deployed Vercel URL → landing page loads without a client
      console error about a failed API call.
- [ ] Specifically open `/vendor/credit-profile?vendor_id=<any-seeded-id>`
      directly (a hard refresh / new tab, not just client-side navigation)
      and confirm the page renders — this route previously broke `next
      build` in one of the two merged candidates if the Suspense fix
      wasn't present; this is the regression test for that fix.

## Close the loop: CORS
- [ ] Back on Render → Environment tab → update `CORS_ORIGINS` to your real
      Vercel URL (and any preview-deployment URL pattern you use),
      comma-separated, e.g.
      `https://hawkercredit.vercel.app,https://hawkercredit-git-main-yourteam.vercel.app`
- [ ] Save → confirm the service redeploys.
- [ ] Reload the Vercel frontend and confirm API calls still succeed (no
      new CORS console errors).

## UptimeRobot
- [ ] Create a new HTTP(s) monitor.
- [ ] URL: `https://<your-render-service>.onrender.com/health`
- [ ] Interval: your choice (Render free tier sleeps on inactivity, so a
      5-minute interval is reasonable to keep it warm).
- [ ] Confirm the first check comes back "Up".

## Login (all three roles)
- [ ] Vendor: `vendor@hawkercredit.com` / `vendor123` → lands on vendor
      dashboard.
- [ ] Lender: `lender@hawkercredit.com` / `lender123` → lands on lender
      dashboard.
- [ ] Admin: `admin@hawkercredit.com` / `admin123` → lands on admin
      dashboard.
- [ ] For each: refresh the page after login and confirm you're still
      authenticated (session persists across reload).
- [ ] Confirm logout actually clears the session (refresh after logout
      lands you back at login, not the dashboard).

## Vendor dashboard
- [ ] Profile, credit score, repayment probability, and SHAP explanation
      all render with real numbers (not placeholders/blank).
- [ ] Transaction history and cash-flow forecast render.
- [ ] Submitting a loan request succeeds and shows a status.
- [ ] Consent settings page shows existing granted consent (from signup)
      and toggling one off/on actually changes AI feature output on a
      subsequent view (e.g. transaction-based features drop when
      `TRANSACTIONS` consent is revoked).

## Lender dashboard
- [ ] Vendor discovery / search / filter works.
- [ ] Opening a vendor's profile from the pool shows the same
      explainable-AI view, plus the human-review approve/reject panel.
- [ ] Underwriting queue (`/lender/review`) lists pending loan requests and
      approve/reject actually changes their status.
- [ ] Try loading a vendor profile or loan by guessing/editing an ID that
      isn't yours to access as a **vendor** login — confirm you get a 403,
      not the data.

## AI / SHAP
- [ ] A vendor's score is stable across repeated views (deterministic
      given the same underlying data) — not a different random number
      each refresh.
- [ ] Both a technical SHAP breakdown and a human-readable explanation are
      visible on the credit profile page.
- [ ] Synthetic-data disclosure text is visible somewhere on the
      explainability view.

## Quantum / Classical / Benchmark
- [ ] `/lender/portfolio/optimizer` runs and returns a result within a
      reasonable time (seconds, not minutes) for the default candidate pool.
- [ ] The result shows execution status, qubit count, shots, layers,
      runtime, `business_objective`, and the selected vendor list.
- [ ] `/lender/benchmark` shows both quantum and classical results scored
      on the same `business_objective`, with runtime for both.
- [ ] Confirm the displayed portfolio never exceeds the stated capital,
      risk, or per-category concentration limits (post-validation working).
- [ ] Force a small/edge-case candidate pool (e.g. filter to very few
      vendors) and confirm it still returns a valid result or a clear
      error — not a crash.

## Underwriting & Audit
- [ ] An approve/reject decision from either the review queue or a vendor
      profile shows up in `/admin` audit logs with the correct actor and
      timestamp (admin login required to view).
- [ ] Audit log terminology says "append-only application audit log," not
      "immutable."

## Final sanity pass
- [ ] Open browser dev tools → Network tab → confirm no request is going
      to `localhost` from the deployed Vercel site.
- [ ] Confirm no API error response leaks a raw stack trace to the
      frontend UI.
